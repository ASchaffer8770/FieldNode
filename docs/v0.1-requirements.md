# v0.1 — Local Edge Presence

## Goal

Demonstrate that multiple field clients can exchange operational presence and status through a local Linux edge node without relying on WAN connectivity.

## Functional Requirements

### FR-1 Client registration

A client can register with the edge node using a display name and client type.

The edge node assigns a stable UUID for the lifetime of the registered record.

### FR-2 List clients

A client can request the current set of known nodes.

### FR-3 Read client

A client can retrieve one registered node by UUID.

### FR-4 Update status

A registered client can update its status.

Initial status values:

- AVAILABLE
- BUSY
- OFFLINE
- UNKNOWN

### FR-5 Live updates

When a node is registered or its status changes, connected subscribers receive the new node state over the local WebSocket channel.

### FR-6 Health

The service exposes a health endpoint suitable for deployment checks.

## Operational Requirements

### OR-1 WAN independence

FR-1 through FR-6 must continue working when the edge host has no route to the public internet.

### OR-2 Restart survival

Before v0.1 is considered complete, registered node state must survive an edge-service restart.

### OR-3 Reproducible deployment

The edge stack must be startable on a Linux host with documented commands and containerized dependencies.

### OR-4 Diagnosability

Failures must produce useful logs and health information.

## Acceptance Demo

1. Start the FieldNode edge server.
2. Connect Client A and Client B over the same local network.
3. Register both clients.
4. Display both clients in each client's node list.
5. Change Client A to AVAILABLE.
6. Observe the update on Client B without refreshing.
7. Remove WAN access from the edge host.
8. Repeat registration and status updates successfully.
9. Restart the edge service.
10. Verify persisted node state returns.

The first six steps are the initial thin slice. Persistence and restart recovery complete v0.1.
